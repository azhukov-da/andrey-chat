# Specification gaps

Places where the implementation diverges from a specified scenario, found by writing the test the
specification describes and watching it fail.

The rule that produces an entry here, from the `add-backend-integration-tests` change:

1. The test keeps its specification-accurate assertions — it is not rewritten to bless the observed
   behaviour, because that would turn its `@spec:` claim into a false statement.
2. It is marked `Skip` with a reason naming the scenario identifier and what was actually observed.
3. A row lands in the table below, pointing at the source location that produces that behaviour.

`tools/spec-coverage` then reports the scenario as claimed by a test that did not pass, which is a
more useful thing to read than either a permanently red suite or a green one that has quietly
lowered its standards.

A row needs a source location. A divergence that cannot be pinned to one is a test bug, not an
implementation gap.

Nothing here is fixed by that change: application source is out of its scope. This document is the
input to a follow-up change that decides, per row, whether the specification or the implementation
is the thing that should move.

| Scenario | Expected (per spec) | Observed | Source |
|---|---|---|---|
| `authentication/password-reset-by-email/completing-a-reset` | A visitor submitting a valid reset code with a policy-satisfying new password has their password changed and can sign in with it. | `POST /resetPassword` answers `400 {"errors":{"InvalidToken":["Invalid token."]}}` for every account. The token itself is valid — `UserManager.ResetPasswordAsync` accepts the same token in process. Identity's endpoint refuses any account whose email is unconfirmed, and nothing in registration ever confirms one, so the flow is unreachable for every account the application creates. Confirming the address in a probe makes the same request return 200. This also contradicts `user-accounts/self-registration`, which says email verification is not required to use the account. | [BE/Infrastructure/Identity/AuthService.cs](../BE/Infrastructure/Identity/AuthService.cs) `RegisterAsync` creates the user without confirming the email; the refusal is in ASP.NET Core Identity's `MapIdentityApi` `/resetPassword` handler. |
| `messaging/deleting-messages/author-deletes` | A deleted message "stops exposing its text" and renders as a placeholder for everyone. | `GET /api/rooms/{id}/Messages` returns the deleted message with its original `text` intact and `isDeleted: true`. Any client that ignores the flag — or any caller reading the API directly — still gets the text. Only the pushed `MessageDeleted` event clears it, and only for clients connected at the time. | [BE/Application/Services/MessageService.cs](../BE/Application/Services/MessageService.cs) `GetMessageHistoryAsync`, whose projection sets `Text = m.Text` without consulting `DeletedAt`. |
| `messaging/sending-messages/banned-member-sends` | A user with a ban entry for the room is refused **as banned**. | The post is refused, but with `Room.NotMember`. Banning deletes the `RoomMemberships` row, and `SendMessageAsync` checks membership before it checks bans, so the ban branch is unreachable for anyone actually banned. The refusal is correct; the reason given to the client is not, so the UI cannot tell a ban from never having joined. | [BE/Application/Services/RoomService.cs](../BE/Application/Services/RoomService.cs) `BanMemberAsync` removes the membership; [BE/Application/Services/MessageService.cs](../BE/Application/Services/MessageService.cs) `SendMessageAsync` orders the membership check ahead of the ban check. |
| `chat-rooms/room-creation/missing-name` | A room needs a name; a request without a usable one is refused and creates nothing. | `POST /api/Rooms` with `""` or `"   "` returns `201 Created` and the room exists with that name. The rename path guards the same field — `UpdateRoomAsync` starts with `if (string.IsNullOrWhiteSpace(name))` — so the two paths disagree about whether a name is required. | [BE/Application/Services/RoomService.cs](../BE/Application/Services/RoomService.cs) `CreateRoomAsync`, which goes straight from the authorization check to the uniqueness check. |
| `user-accounts/display-name/setting-a-display-name` | A display name is "an optional display name of at most 50 characters", so a longer one is refused. | `PATCH /api/Me/display-name` returns 204 and stores a 51-character name unchanged. Nothing validates the length on either the request model or the service. | [BE/Application/Services/ProfileService.cs](../BE/Application/Services/ProfileService.cs) `UpdateDisplayNameAsync`; the request model [BE/Web/Models/UpdateDisplayNameRequest.cs](../BE/Web/Models/UpdateDisplayNameRequest.cs) carries no annotation. |
| `user-presence/presence-states/connected-but-idle` | Three states, named `online`, `afk`, and `offline`; the hub's `PresenceChanged` payload and `GetPresenceFor` report the idle one as `afk`, which is the value the frontend's `presenceStore` switches on. | The idle state is `Away`. `GetPresenceFor` returns `"Away"` and the pushed `PresenceChanged` carries `"Away"`, so the name the specification and the client agree on is never produced by the server. | [BE/Application/Abstractions/IPresenceTracker.cs](../BE/Application/Abstractions/IPresenceTracker.cs) `PresenceStatus`, whose third member is `Away`; [BE/Web/Hubs/ChatHub.cs](../BE/Web/Hubs/ChatHub.cs) `GetPresenceFor` serialises the enum with `ToString()`. |
| `unread-notifications/unread-indicators/message-arrives-in-a-background-chat` | A message arriving in a chat the recipient is not reading raises that chat's unread count, and the count is the server's, so it survives a reload and is the same on another device. | No unread count is ever computed or pushed. `IChatNotifier.UnreadUpdatedAsync` is implemented but has no caller anywhere in the application, and `SendMessageAsync` does not derive a count, so `UnreadUpdated` never reaches a client. The membership's `LastReadMessageId` is recorded, so the data a count would be derived from exists; nothing derives it. | [BE/Application/Services/MessageService.cs](../BE/Application/Services/MessageService.cs) `SendMessageAsync`, which notifies `MessageReceivedAsync` only; [BE/Web/Hubs/ChatNotifier.cs](../BE/Web/Hubs/ChatNotifier.cs) `UnreadUpdatedAsync` is dead code. |
| `attachments/uploading-attachments/banned-uploader` | An upload by a user banned from the room is refused **as banned**. | The upload is refused, but with `Room.NotMember`. This is the same mechanism as the messaging row above: banning deletes the `RoomMemberships` row, and the upload endpoint checks membership before it checks bans, so the ban branch is unreachable for anyone actually banned. The refusal is correct; the reason is not. | [BE/Web/Controllers/AttachmentsController.cs](../BE/Web/Controllers/AttachmentsController.cs) `Upload`, whose membership check returns `Room.NotMember` before the `RoomBans` query runs; [BE/Application/Services/RoomService.cs](../BE/Application/Services/RoomService.cs) `BanMemberAsync` removes the membership. |
| `attachments/transcription-eligibility-length-limit/long-voice-attachment-uploads-without-a-transcript` | An audio attachment longer than ten minutes uploads and plays as normal, and **no transcription job is enqueued for it**. | Every audio upload is enqueued unconditionally. Nothing in the application knows a clip's duration — the `Attachment` entity records size and kind but no length — so the ten-minute ceiling is passed to the transcription backend as `max_duration_seconds` and enforced there, which answers `audio_too_long`. The end state the requirement describes does hold (no caption, nothing shown to other participants); the scenario's condition, that no job is enqueued, does not. | [BE/Web/Controllers/AttachmentsController.cs](../BE/Web/Controllers/AttachmentsController.cs) `Upload` enqueues for every `AttachmentKind.Audio`; [BE/Infrastructure/Services/FasterWhisperTranscriptionService.cs](../BE/Infrastructure/Services/FasterWhisperTranscriptionService.cs) turns the backend's `audio_too_long` into `Transcription.TooLong`. |
| `speech-to-text/dictation-length-limit/oversized-clip-submitted-directly` | A clip longer than 120 seconds is rejected as a bad request stating the limit, **and no transcription is attempted** — so the limit holds even when the client is bypassed. | Every clip is forwarded. `POST /api/transcribe` has no way to measure the audio it is given: it passes 120 seconds to the transcription backend as `max_duration_seconds` and relies on that backend to answer `audio_too_long`, which it then turns into a 400 naming the limit. The refusal the caller sees is right; it costs a round trip to the backend, and with the backend unreachable an over-long clip is reported as unavailable rather than as too long. Same shape as the attachments row above. | [BE/Web/Controllers/TranscriptionController.cs](../BE/Web/Controllers/TranscriptionController.cs) `Transcribe`, which goes from the zero-length check straight to `TranscribeAsync`. |
| `authentication/persistent-login/keep-me-signed-in` | Signing in with "keep me signed in", closing the browser and reopening the application restores the session without re-entering credentials. | The refresh token is written to `localStorage` exactly as the choice promises, but reopening the browser lands on the sign-in screen. Nothing in the application ever reads it back: `useAuth.bootstrapAuth` is the only code that would exchange a persisted refresh token at startup, and its sole callers are unit tests. `AppShell` gates on the access token, which always lives in `sessionStorage` and so is always absent after a restart, and redirects to `/login` before any refresh is attempted. The storage half of the feature is built; the restore half is not wired in. | [FE/src/hooks/useAuth.ts](../FE/src/hooks/useAuth.ts) `bootstrapAuth`, which has no call site in application code; [FE/src/features/layout/AppShell.tsx](../FE/src/features/layout/AppShell.tsx), whose effect navigates to `/login` whenever `accessToken` is null. |
